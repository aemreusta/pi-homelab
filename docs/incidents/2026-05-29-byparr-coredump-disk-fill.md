# 2026-05-29 — byparr core dumps silently filled 132G of the SSD

- **What happened:** Routine disk-usage analysis found the root SSD at 91% (158G free). 142G of it was byparr's container writable layer — 2,101 Firefox/Camoufox core dumps (132G) piled into `/app` between May 21 and May 29. Cleared them (`rm -f /app/core.*`) → 131G reclaimed, 84%.
- **Why:** Camoufox crash-loops on nearly every request. Host `kernel.core_pattern=core` writes each crash's core to the process CWD (`/app`); byparr has no bind mount for `/app`, so cores landed in the overlay upper-dir — invisible to `du /srv`, counted against the disk.
- **Class:** byparr Camoufox instability (browser-process leak) — same root container as the PID/zombie leak, new on-disk symptom. Also a "leak hidden in a container writable layer where `du /srv` can't see it" shape.
- **Occurrence:** Disk-symptom 1st. Underlying byparr leak Nth — see the 2026-05-21 byparr PID/zombie storm. The weekly restart cron masks live PIDs but never cleaned cores (they persist until the container is recreated).
- **Structural fix:** Two layers, both shipped. (1) Per-container `ulimits: core: 0` on byparr in `ansible/roles/media/templates/docker-compose.yml.j2` (verified live: `ulimit -c` = 0 inside container). (2) Host-wide `kernel.core_pattern = |/bin/false` in `common` role `sysctl_settings` (`inventory/group_vars/all/main.yml`) — containers inherit the host's `core_pattern` (they have no own), so this discards cores for EVERY container, stopping any future container from repeating the trick. Underlying Camoufox crashes still unfixed (upstream); cores are no longer a disk problem.
