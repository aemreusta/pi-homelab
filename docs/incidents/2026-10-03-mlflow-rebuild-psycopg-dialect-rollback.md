# 2026-10-03 — MLflow rebuild crash-looped on SQLAlchemy 2.1's psycopg default; CD rolled back

- **What happened:** `deploy-v2026.10.03.2` touched only a comment in `mlflow/files/Dockerfile`, which still rebuilds the image (`build: always`, unpinned). At 13:55 TRT `mlflow db upgrade` failed with `ModuleNotFoundError: No module named 'psycopg'` three times. The CD marked the deploy failed at 14:08 and began rolling back every role to the previous tag. The new `mlflow` container crash-looped (31 restarts), so MLflow was down from about 14:00.
- **Why:** The image tracks latest with no pins. SQLAlchemy 2.1 (2.1.3 pulled) maps a bare `postgresql://` URI to the `psycopg` (v3) dialect; `requirements.txt` installed only `psycopg2-binary`. The break was latent upstream and surfaced at the first rebuild after the release. Rollback cannot repair it: the previous tag rebuilds the same latest dependencies. Confirmed live: the CD logged `ROLLBACK FAILED at mlflow` at 15:06 TRT after re-deploying the earlier roles, then picked up the fix tag at 15:08.
- **Class:** An unpinned dependency drifts upstream and breaks at an unrelated rebuild. Same family as the [victoria-logs distroless healthcheck break](2026-07-16-victorialogs-distroless-image-broke-exec-healthcheck.md) (vendor `latest` changing under an assumption). New aspect: a rollback-on-failure CD is no safety net for floating dependencies.
- **Occurrence:** 2nd for "track-latest drift breaks a deploy"; 1st where it triggered a full CD rollback.
- **Structural fix:** `requirements.txt` installs `psycopg[binary]`, verified against mlflow 3.16.1 / SQLAlchemy 2.1.3. [`tests/test_mlflow_image.py`](../../tests/test_mlflow_image.py) now asserts that the driver the backend URI loads is installed. Shipped forward in `deploy-v2026.10.03.3`. Open: a pre-deploy build smoke for custom images, so latest-drift fails in CI instead of on the Pi.
