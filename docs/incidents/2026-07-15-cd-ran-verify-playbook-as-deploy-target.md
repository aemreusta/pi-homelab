# 2026-07-15 — CD ran a *verification* playbook as a deploy target, rolling back the domain-migration tag

- **What happened:** `deploy-v2026.07.15.1` (the `example.internal` clean-cut) was picked up by the CD and **rolled back**. The plan had 14 targets — `verify-ntfy` plus the changed service roles (`alertmanager`, `authelia`, `homepage`, `label-studio`, `media`, `traefik`, `vmalert`, …) — and `verify-ntfy` sorted **first**, failed `3/3 (rc=2)`, so `deploy FAILED at target verify-ntfy` → rollback → the rollback re-ran the same target → `ROLLBACK FAILED at verify-ntfy`. **Net effect on the box: nothing.** Because the failure hit the *first* target, no role was deployed and — critically — none was reverted either: the live migration (deployed manually beforehand) stood intact (`*.example.internal` rewrite present, DNS resolving, services up). The commit was left held (`failed_sha`).
- **Why:** Two bugs stacked. (1) **`plan_targets` treats any changed `ansible/playbooks/<name>.yml` as a deploy target.** I edited `playbooks/verify-ntfy.yml` as part of the domain migration, so the CD dutifully "deployed" it — but a `verify-*` playbook *verifies* live state, it does not deploy it. (2) **`verify-ntfy.yml` was not check-mode safe:** the CD runs `--check --diff` before apply; `ansible.builtin.command` is skipped under `--check`, so `verify_ntfy_host_lookup` registered as a bare `{skipped: true}` dict and the next task's `verify_ntfy_host_lookup.stdout.split()[0]` crashed at arg-finalization → rc=2. `make verify-ntfy` passed for me locally precisely because a bare `make` has **no `--check` phase** — the "works locally, fails under autodeploy = diff the INVOCATION" meta-lesson, again ([ops-discipline §6](../operations/ops-discipline.md)).
- **Class:** (a) **check-mode-skip** — a `--check`-skipped task's register consumed by a later task. 4th instance, and the 3rd distinct accessor: `uri`→`.json` (2026-07-02), `uri`→`.content` (adguard, 2026-07-14), now `command`→`.stdout`. The guard test only covers `uri`, so it could not have caught this. (b) **NEW: non-deployable playbook auto-run as a deploy target** — beyond the check-mode crash, this is dangerous by design: a verification that *legitimately fails* (its whole job) would roll back every other role in the plan. A red test must never revert a good deploy.
- **Occurrence:** 1st of the verify-as-deploy-target shape. 4th of the check-mode-skip class.
- **Structural fix:** (1) `plan_targets` now returns **no target** for `playbooks/verify-*.yml` (not even a held one — it is simply not a deployment), guarded by `test_verify_playbook_is_not_a_deploy_target` + `test_verify_playbook_does_not_poison_a_real_plan` (RED before, GREEN after; `make cd-drill` still green). (2) `verify-ntfy.yml`'s four read-only probes get `check_mode: false` so they actually run under `--check` and their asserts can't crash — correct for a read-only verification. Controller ships via a deliberate `make homelab-autodeploy` bootstrap (it is on `never_auto`). **Tell for next time:** a green `make verify-x` does NOT mean the CD can run it — the CD adds a `--check` phase the bare `make` never exercises. And when adding a new `ansible/playbooks/*.yml`, ask whether it is a *deployment* at all before the CD decides for you.
