# 2026-07-14 — CD self-sabotaging rollback: zot check-mode htpasswd bug reverted the controller mid-cycle

- **What happened:** First `deploy-v*` tag under the new full-rollout CD (`deploy-v2026.07.14.1`). The controller planned correctly (zot/vmalert/homepage/homelab-autodeploy, base excluded), but `zot` failed its deep-check 3×/rc=2 and the deploy rolled back. The rollback did `git reset --hard <last-good=65caf7e>` and redeployed the *attempted* targets at that old commit — which, because full-rollout had made `homelab_autodeploy` itself auto-deployable, **redeployed the controller at 65caf7e, reverting its own live logic** (full-rollout + `never_auto` gone, back to the pilot allowlist) and reverting homepage (drawer/readability) + vmalert (zot rules). The reverted rollback then re-hit the same zot bug and thrashed for ~27 min (load ~7.9) until manually `pkill -9`'d.
- **Why:** Two bugs stacked. (1) **zot check-mode-unsafe**: `community.general.htpasswd` writes `/tmp/.zot_htpasswd_<host>` but makes no change under `--check`, so the file is absent; the next `copy: src=` then fails its check-mode diff (`Could not find or access /tmp/.zot_htpasswd_homelab`). It passed every manual `make zot` only because a prior real run left the file in the *Mac's* `/tmp`; the CD deep-check runs on the Pi (`--connection=local`) with a clean `/tmp` and failed every time. (2) **self-sabotaging rollback**: the rollback redeploys `homelab_autodeploy`, so a failed deploy reverts the very controller driving the recovery.
- **Class:** (a) check-mode-skip class — a `--check`-skipped task's output consumed by a later task's check-mode diff (sibling of the [`uri`-skip brick](2026-07-02-autodeploy-strict-templating-brick-loop.md) / `test_uri_check_mode_safety.py`); masked by a stale controller-local temp file so it only bites where `/tmp` is clean. (b) self-sabotaging-rollback class (the repo's agent rules flag `homelab_autodeploy` as load-bearing) — the CD reverting its own control logic mid-cycle.
- **Occurrence:** 1st for both — the zot htpasswd temp-file pattern (other roles that hash on the controller and `copy: src=` a temp file share the shape) and the controller-reverts-itself rollback (new, enabled by the 2026-07-14 full-rollout making the controller auto-deployable).
- **Structural fix:** (1) `check_mode: false` on the zot htpasswd-generate task so the temp file is regenerated even in `--check` and the copy always has a source (validated: `--check` with clean `/tmp` now `ok=30 failed=0`). (2) Added `homelab-autodeploy` to `homelab_autodeploy_never_auto_targets` (now `[base, homelab-autodeploy]`): the controller is NEVER auto-deployed — controller changes ship via a deliberate manual `make homelab-autodeploy` bootstrap, so neither a tag nor a rollback can auto-ship/self-revert it. Recovery: `pkill -9` the stuck run + clear lock, `make zot/homepage/vmalert/homelab-autodeploy` to restore live state to HEAD, re-tag once green. Tell for next time: a CD deploy that fails on `--check` but passes local `make` → suspect a `--check`-skipped prerequisite masked by controller-local state; diff the controller (`Mac` vs `Pi --connection=local`), not the role.
