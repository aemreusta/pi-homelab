# 2026-06-25 — Zot rejected every image push (HTTP 415); the build→Zot push path had never actually worked

- **What happened:** Standing up the Mac CI runner, the first-ever push to the local Zot registry (`raspberrypi.local:5050`) failed with docker's "manifest invalid". A busybox push failed identically, and `/v2/_catalog` was empty — proving **nothing had ever been pushed** since Zot shipped (2026-06-23), despite PRD 013 documenting the build→Zot→deploy path as working.
- **Why:** Zot v2.1.17 is OCI-native and returns **HTTP 415 (Unsupported Media Type)** for Docker schema2 manifests (`application/vnd.docker.distribution.manifest.v2+json`) unless `http.compat: ["docker2s2"]` is set. OrbStack's `docker push`/buildx sends exactly that media type. Docker mapped the 415 to the misleading client-side "manifest invalid", which sent diagnosis toward the *image* (provenance, schema, format) when the registry config was the cause. Only the Zot container log (`statusCode:415` on every `PUT .../manifests/...`) named it.
- **Class:** Feature shipped + documented as working but **never exercised end-to-end** → latent total failure, invisible until first real use. Sibling of the delivery-blind-spot class (health check proves the service is *up*, not that the *operation* works).
- **Occurrence:** 1st for Zot. The "valid-but-unexercised" shape rhymes with the ntfy subscribers=0 delivery blind spot and the silent-cron class (green liveness, broken function).
- **Structural fix:** Shipped — `zot_compat: ["docker2s2"]` default + `http.compat` in the zot config template (this commit); verified the runner + supervisor images push and appear in `/v2/_catalog`. Follow-up worth doing: a tiny post-deploy smoke push (push+pull a 1-layer image) in the zot role or a CI check, so "registry accepts a push" is asserted, not assumed — the gap here was that liveness (`up`/`ZotDown`) was monitored but **push capability never was**.
