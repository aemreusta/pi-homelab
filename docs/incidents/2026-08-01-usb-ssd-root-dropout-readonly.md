# 2026-08-01 — Second USB SSD browned out the root SSD; root fs went read-only for ~15 min, silently

- **What happened:** A 1 TB Kingston XS1000 was attached to the Pi's second USB3 port and the Pi was rebooted. During boot both SSDs spun up at once; the **root** SanDisk Portable SSD (`usb 2-1`) dropped off the bus mid spin-up, `Read Capacity` failed, and it was registered as a **0-byte disk**. It re-enumerated and the host booted, but ~8 minutes later the device vanished again and came back as `/dev/sdc` while `/` was still mounted on the now-nonexistent `/dev/sdb`. ext4 honoured `errors=remount-ro`. For ~15 minutes sshd reset every connection, 40 of 41 containers were down, AdGuard DNS was dead — and **not one alert fired**. Discovered by hand while investigating an unrelated question.
- **Why:** The Pi 4B's USB ports share a ~1.2 A budget across a single 5 Gbps xHCI controller. Two bus-powered USB3 SSDs (~0.9 A peak each) on that controller exceed it during concurrent spin-up. `vcgencmd get_throttled` read `0x0` throughout, which is not a contradiction: it measures the SoC supply rail, not per-port USB current. The alerting silence has a separate cause — vmalert, Alertmanager and ntfy all live on the disk that failed, so the observability stack died with the thing it was meant to observe. node_exporter survived only by accident of being host-networked, already resident, and read-only; it was exporting `node_filesystem_readonly{mountpoint="/"} 1` the entire time and nothing was looking at it.
- **Class:** Two classes. (1) **Shared-resource exhaustion from an additive change** — attaching hardware to a saturated bus degrades the *existing* device, not the new one. (2) **Self-referential observability** — an alerting stack cannot report the failure of the storage it runs on. Closely related to the ntfy silent-delivery class (2026-06-06, 2026-07-16): all-green dashboards, zero delivery.
- **Occurrence:** 1st for the USB power-budget class. 3rd for the "alerting was silent during a real outage" family — see [2026-06-06 ntfy subscribers-zero](2026-06-06-ntfy-silent-delivery-subscribers-zero.md) and [2026-07-16 ntfy em-dash header crash](2026-07-16-ntfy-bridge-emdash-title-crashed-delivery.md). Those two were delivery-path failures; this one is an evaluator failure, which is worse — nothing even computed that something was wrong.
- **Structural fix:** **Shipped** — `RootFilesystemReadOnly` vmalert rule on node_exporter's in-memory `node_filesystem_readonly` (the one signal that survives a read-only root), plus a kernel storage-fault scanner ([`kernel_io_scan.py`](../../ansible/roles/node_exporter/files/kernel_io_scan.py) + [`kernel-io-scan.sh.j2`](../../ansible/roles/node_exporter/templates/kernel-io-scan.sh.j2), cron */5) emitting `homelab_kernel_io_events` in three tiers (fatal / dropout / precursor) with rules `HostStorageFaultsFatal`, `HostStorageLinkDropout`, `HostStorageFaultsPrecursor`, `KernelIOScanStale`. Validated against this incident's real `journalctl -k -b -1`: it scores `disk_zero_capacity=4` (crit) and `usb_disconnect=1` (warn), and scores clean on a healthy boot. Firing drill verified end-to-end to ntfy (`http=200`). **Deferred** — the out-of-band watchdog. Everything above still runs on the Pi, so a hard-enough disk failure remains unalertable; only an off-Pi evaluator (Mac worker scraping `:9100`) closes that. Tracked as a follow-up. **Operational** — do not reattach a second bus-powered drive without a powered USB3 hub; plan in [docs/design/042-second-ssd-integration-plan.md](../design/042-second-ssd-integration-plan.md).

## Detail worth keeping

Two findings that shaped the fix and would otherwise be re-derived:

1. **The evidence for a root-fs failure cannot be written to the root fs.** `journalctl -k -b -1` for the incident boot contains the `USB disconnect` but **no** ext4 error and **no** "Remounting filesystem read-only" — journald could not write once the disk went read-only. Its last kernel lines are UFW BLOCK noise. This is why the scanner reads `dmesg` (in-RAM ring buffer) rather than journald, and why `node_filesystem_readonly` — computed in node_exporter's memory — is the authoritative live signal for the terminal state.

2. **The only logged precursor was a single line.** `usb 2-1: USB disconnect, device number 2`. A "≥2 occurrences" threshold — the obvious anti-flapping default — would have missed the entire incident. Hence the `dropout` tier: for a host where every drive is permanently attached, one disconnect is signal, and the occasional benign firing when the operator physically adds a drive is the correct trade.

## Verified undamaged

Checked after recovery, all clean: ext4 `Filesystem state: clean`, zero recorded FS errors, zero I/O errors on the current boot, `throttled=0x0`. SQLite `PRAGMA integrity_check` ok on `sonarr.db`, `radarr.db`, `prowlarr.db`. Full `pg_dump` read of every Postgres database (incl. `authelia`, `mlflow`, `label_studio`) completed clean. 41/41 containers back up.
